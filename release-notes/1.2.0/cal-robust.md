### Fixed

- Calendar: a connection whose sign-in Microsoft no longer accepts (password reset, disabled account, revoked consent, a sign-in policy that now needs the person present — `invalid_grant` / `interaction_required`) is now marked *not authorised*, keeps Microsoft's reason in the new **Authorization Lost** field, and its user gets one notification. It is no longer retried every 15 minutes and Event saves no longer log an error for it. Timeouts and server errors from Microsoft never mark a connection. (#24)
- Calendar: token refreshes no longer save the Microsoft Calendar document. This removes the `TimestampMismatchError: ... (Microsoft Calendar) has been modified after you have opened it` failures of the calendar pull, and a person with the connection form open can still save it after a background refresh. Concurrent refreshes of one connection are serialised: the second worker uses the token the first one minted instead of refreshing again. (#25, token part)
- Calendar: Microsoft Graph throttling is handled as Microsoft asks. 429 and 503 are retried up to three times, waiting what `Retry-After` says — in seconds or as an HTTP date — or with an exponential backoff when it says nothing; 504 is retried for requests that are safe to repeat (never for creating an event). When the wait is longer than a call can hold (10 seconds with a person waiting, 60 seconds in a background job) or the refusals outlast the retries, the connection is left alone for the rest of the run: the push stops instead of failing every remaining event, and the sync reports that Microsoft is throttling. (#26)
- Calendar: re-authorising a connection with a different Microsoft account now starts a clean sync. The delta links, resume point, last-sync watermark and calendar id of the old account are cleared and the new account's default calendar is picked up. Events created in Frappe and pushed to the old account are unlinked (their Microsoft id is cleared and *Sync with Microsoft Calendar* is unticked) so they are neither patched into the wrong mailbox nor re-created with a second round of invitations; tick one again to send it to the new account. Events pulled from the old account stay as they are. A comment on the connection records the switch. (#29)
- Doctor: authorised scopes are now tracked per connection. The doctor reports each connection that signed in before a capability was added, and each connection that has to be authorised again, instead of judging every connection by whoever signed in last. (#30)

### Added

- Microsoft Calendar fields: **Microsoft Account ID** (the account the connection signed in as), **Authorization Lost** (why Microsoft stopped accepting the sign-in) and **Authorized Scopes** (what the connection asked for when it last signed in). All three are written only by the app.

### Upgrade notes

- **Dead connections are marked on the first run after upgrading.** A connection whose refresh token is already rejected by Microsoft is marked *not authorised* the next time anything refreshes its token (usually the first scheduled sync), and its user receives a notification (and email, if their notification settings send one) asking them to sign in again. Sites with many broken connections will see a burst of these notifications once. Live connections are not affected: only `invalid_grant` and `interaction_required` mark a connection.
- If you tick a new capability (for example Teams) and the tenant has not consented to it, Microsoft refuses the next token refresh with `invalid_grant`; that connection is then marked and its user asked to sign in again, which is what it needs to pick up the new permission.
- Migrate copies the site-wide *Authorized Scopes* value onto every authorised Microsoft Calendar (patch `copy_authorized_scopes_to_calendars`), so nobody is asked to re-authorise because of the upgrade. Connections authorised before 1.2.0 record their Microsoft account id at their next sign-in; until then a re-authorisation compares the account's addresses.
- A token refresh is now a commit point: the new tokens are committed immediately so other workers can use them.
- A throttled mailbox is no longer called repeatedly within one run; whatever is left is done by the next scheduled sync. A sync may now sit out up to 60 seconds of Microsoft's requested wait inside a background job.
